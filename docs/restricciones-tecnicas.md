# Restricciones técnicas

> Versión Markdown de la hoja de cálculo del equipo, para la entrega del 28-10-2026. Revisión del 22-10-2026: alineada con los ADR vigentes (disponibilidad del canal WhatsApp en 99,5 % según ADR-0010; telemetría GPS y ETA fuera del alcance de V1 según ADR-0005; proveedor de WhatsApp definido en ADR-0008; flujo Git de ADR-0018). Las filas que quedan fuera de alcance se conservan por trazabilidad y lo indican.

## RestriccionesTécnicas

| Tipo | Categoria | Restricción técnica | Justificación |
| --- | --- | --- | --- |
| Propia del producto | Prácticas de diseño | El diseño y la implementación deben aplicar principios SOLID y mantener bajo acoplamiento y alta cohesión entre componentes. | La mantenibilidad es un atributo crítico de FlowRide. Las reglas de negocio, integraciones y persistencia deben poder evolucionar con impacto localizado. SOLID sirve como restricción de diseño para evitar clases con responsabilidades mezcladas, dependencias rígidas y extensiones que obliguen a modificar código estable. |
| Propia del producto | Estructura de software | La solución debe preservar separación explícita entre dominio, aplicación, infraestructura y mecanismos de entrada, con dependencias dirigidas hacia el núcleo de negocio. | La lógica de transporte no debe depender de Entity Framework, proveedores de identidad, WhatsApp ni detalles de despliegue. La estructura actual Domain / Application / Infrastructure / API se conserva como base porque permite sustituir implementaciones externas sin contaminar el dominio, independientemente de la arquitectura general que se documente en su ADR. |
| Propia del producto | Modelado de dominio | El dominio debe modelarse con DDD, lenguaje ubicuo y límites claros entre responsabilidades operativas; se mantienen modelos anémico y enriquecido como representaciones complementarias del mismo dominio. | FlowRide contiene reglas específicas sobre solicitudes, asignaciones, viajes, conductores, vehículos, telemetría, calificaciones y restricciones regulatorias. El modelado debe reflejar esas reglas de negocio y no reducirse a estructuras CRUD o tablas sin comportamiento ni contexto. |
| Propia del producto | Plataforma tecnológica | El backend de FlowRide se desarrolla en C# sobre .NET 10. | .NET 10 cubre las necesidades actuales de API, asincronía, seguridad, observabilidad y ejecución multiplataforma. Mantener un único stack backend evita introducir complejidad tecnológica sin un driver que la justifique. |
| Propia del producto | Interoperabilidad | Las interfaces síncronas del backend deben exponerse mediante HTTP/HTTPS y JSON; las integraciones orientadas a eventos externos, como WhatsApp, deben ingresar mediante webhooks autenticados y validados. | El Panel Web consume la API directamente y WhatsApp funciona como integración externa. Esta restricción mantiene contratos tecnológicos simples y estándar, permite desacoplar proveedores concretos y facilita pruebas de integración y observabilidad. |
| Propia del producto | Persistencia | PostgreSQL es el motor relacional principal para los datos transaccionales de cada instancia de FlowRide. | El núcleo operativo requiere integridad referencial, transacciones y consultas relacionales sobre usuarios, solicitudes, asignaciones y viajes. PostgreSQL se mantiene como base transaccional vigente; necesidades especializadas como series temporales de telemetría pueden utilizar mecanismos adicionales siempre que no alteren el contrato transaccional del núcleo. |
| Impuesta por negocio | Multi-tenancy | Cada operador de transporte debe estar físicamente aislado de los demás tenants mediante un modelo Silo; el aislamiento entre operadores no puede depender únicamente de filtros lógicos por empresaId. | Un tenant de FlowRide es un operador de transporte. La confidencialidad entre operadores y la contención de fallos son requisitos de negocio. empresaId se conserva únicamente para identificar al cliente empresarial atendido dentro de la base del operador, por ejemplo una aerolínea, minera u hospital. |
| Propia del producto | Autenticación y autorización | La solución de identidad debe estar desacoplada del dominio, utilizar tokens firmados para las sesiones del API, soportar autorización por roles y permitir revocación efectiva de acceso en un máximo de 60 segundos. | La autenticación debe permitir RBAC para Pasajero, Conductor, Administrador del operador y Operador logístico, revocación rápida y validación segura de sesión. El aislamiento entre tenants se resuelve por Silo y no puede depender de un claim empresaId. |
| Impuesta por proveedor externo | Integración WhatsApp | La integración debe utilizar la API oficial de WhatsApp Business y quedar encapsulada detrás de un adaptador que evite acoplar la lógica de negocio a Twilio, Meta Cloud API u otro proveedor concreto. | WhatsApp es el único canal funcional para pasajeros y conductores. El proveedor quedó definido en ADR-0008: el número de prueba de Meta (WhatsApp Cloud API) para el alcance académico, detrás de `IWhatsAppGateway`, con evolución a un número propio sin cambiar el dominio. El webhook debe validar autenticidad, manejar reintentos e idempotencia y respetar las políticas de plantillas y ventanas conversacionales de Meta. |
| Impuesta por operación | Telemetría GPS | **Fuera del alcance de V1** (RF-55, RF-56; ADR-0005 en estado *Proposed*). Se conserva por trazabilidad: la plataforma debe soportar una ingesta sostenida de al menos 100 eventos de ubicación por minuto por instancia y conservar la telemetría GPS durante 6 meses. | El dimensionamiento vigente considera hasta 50 conductores/vehículos reportando ubicación aproximadamente cada 30 segundos. La telemetría se utiliza para monitoreo y detección de desviaciones de ETA; no puede convertir el motor de asignación en un esquema de reasignación dinámica por cercanía. |
| Impuesta por operación | Rendimiento | Las operaciones CRUD críticas deben cumplir P95 < 500 ms y P99 < 1,5 s; las consultas de estado P95 < 300 ms y P99 < 1 s; los reportes operacionales P95 < 2 s y P99 < 5 s. | El dimensionamiento vigente es de hasta 200 usuarios simultáneos por instancia. Las metas se expresan por percentiles y tipo de operación para que sean medibles y representen el comportamiento real del sistema bajo carga. |
| Impuesta por operación | Disponibilidad | La solución debe diseñarse para objetivos de disponibilidad diferenciados: 99,5 % para el canal WhatsApp (revisado desde 99,9 % en ADR-0010), 99,5 % para el motor de asignación y operaciones críticas, y 99 % para el Panel Web Administrativo. | No todos los componentes tienen el mismo impacto operacional. La disponibilidad, recuperación, monitoreo y alertamiento deben priorizarse según estos tiers y no mediante un único porcentaje general para toda la plataforma. |
| Propia del producto | Consistencia | Las operaciones que cambian simultáneamente solicitud, asignación, conductor, vehículo o viaje deben preservar atomicidad y no dejar estados parciales o contradictorios ante fallos o concurrencia. | La asignación es el núcleo operativo de FlowRide. Si falla una conexión o dos procesos compiten por el mismo conductor, el sistema debe mantener una única verdad transaccional. El patrón concreto de consistencia y publicación de eventos se documentará en la decisión arquitectónica correspondiente. |
| Propia del producto | Caché | La caché solo puede utilizarse para datos de consulta frecuente y baja volatilidad; nunca puede convertirse en fuente de verdad para solicitudes, asignaciones, viajes en curso o telemetría. | Cualquier tecnología de caché debe respetar el aislamiento Silo, utilizar invalidación explícita y evitar información obsoleta en datos operacionales críticos. La implementación concreta puede variar sin cambiar esta restricción. |
| Propia del producto | Observabilidad | Los eventos técnicos y operativos críticos deben registrarse de forma estructurada e incluir como mínimo traceId, identificador del tenant, timestamp, componente y resultado de la operación. | FlowRide necesita reconstruir flujos completos desde la recepción de una solicitud hasta la asignación, notificación y viaje. La observabilidad debe permitir correlación entre API, motor, integraciones y telemetría sin mezclar datos de operadores distintos. |
| Impuesta por negocio | Seguridad de datos | Toda comunicación externa debe utilizar cifrado en tránsito y los datos sensibles deben protegerse en almacenamiento según su riesgo; el acceso a información personal y ubicación debe estar limitado por rol y contexto operacional. | La plataforma procesa datos personales y telemetría GPS. La seguridad no puede depender únicamente de autenticación: debe existir defensa en profundidad sobre transporte, persistencia, autorización, auditoría y exposición mínima de datos. |
| Impuesta por negocio | Costo operacional | La plataforma tecnológica debe poder operar dentro de un objetivo aproximado de 20 a 40 USD mensuales de infraestructura básica por tenant, sin contar costos variables razonables del canal WhatsApp. | El pricing previsto de 150 a 500 USD mensuales por instancia obliga a que autenticación, persistencia, observabilidad, almacenamiento y despliegue mantengan una relación costo/beneficio sostenible. Una alternativa técnicamente superior puede descartarse si vuelve inviable el modelo por tenant. |
| Propia del producto | Control de versiones y calidad | El código fuente debe gestionarse con Git/GitHub, trabajo por ramas, revisión mediante Pull Request y análisis estático automatizado antes de integrar cambios a develop y a main (ADR-0018). | La trazabilidad del código y la detección temprana de defectos son parte de la línea base técnica. Se implementó con GitHub Actions: compilación sin advertencias, formato, pruebas con cobertura, verificación del frontend y escaneo de secretos con gitleaks (también como hook antes de cada push); SonarCloud queda como complemento opcional. |
| Propia del producto | Código y pruebas | La implementación debe aplicar prácticas de Clean Code y mantener pruebas automatizadas sobre las reglas de negocio y los flujos críticos. | Nombres claros, funciones acotadas, ausencia de código muerto y pruebas repetibles reducen el costo de cambio. Las abstracciones de repositorios e integraciones deben permitir sustituir infraestructura real por dobles de prueba sin modificar la lógica del dominio. |
