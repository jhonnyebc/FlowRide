# Funcionalidades significativas

> Versión Markdown de la hoja de cálculo del equipo, para la entrega del 28-10-2026. Revisión del 22-10-2026: alineada con los ADR vigentes (disponibilidad del canal WhatsApp en 99,5 % según ADR-0010; telemetría GPS y ETA fuera del alcance de V1 según ADR-0005; proveedor de WhatsApp definido en ADR-0008; flujo Git de ADR-0018). Las filas que quedan fuera de alcance se conservan por trazabilidad y lo indican.

## RequisitosFuncionales

| Nombre Requisito Funcional | Especificación |
| --- | --- |
| RF-01-Autenticación mediante mecanismo de identidad basado en token | El sistema deberá autenticar y validar la identidad de los usuarios mediante un mecanismo basado en tokens y un proveedor de identidad desacoplado. El sistema usa un proveedor de identidad desacoplado y tokens de acceso estándar; la comparación y selección del proveedor se documenta en ADR-03. |
| RF-02-Autorización basada en roles | El sistema deberá validar en cada petición a endpoints protegidos que el usuario posea el rol requerido para ejecutar la acción, rechazando la petición si no cumple. |
| RF-03-Registro de operador de transporte como tenant | El sistema deberá permitir registrar un nuevo operador de transporte como tenant de FlowRide y aprovisionar su entorno de datos aislado físicamente mediante el modelo Silo. |
| RF-04-Configuración inicial del tenant | El sistema deberá permitir configurar los parámetros base de operación del tenant: usuarios administrativos, recursos operativos y parámetros necesarios para iniciar la operación. |
| RF-05-Creación de usuarios por tenant | El sistema deberá permitir al administrador crear usuarios del tenant (pasajeros, conductores, operadores logísticos y administradores) con el rol y asociación operacional correspondiente. |
| RF-06-Asignación de roles a usuarios | El sistema deberá permitir asignar o modificar el rol de un usuario existente dentro de la empresa (Pasajero, Conductor, Operador Logístico, Administrador). |
| RF-07-Consulta de disponibilidad de conductores | El sistema deberá permitir consultar los conductores disponibles para una franja o servicio dentro del tenant, filtrando por estado y criterios operativos programados. La ubicación GPS no se utiliza para reasignación dinámica por cercanía. |
| RF-08-Registro de itinerarios | El sistema deberá permitir registrar itinerarios de transporte que definen los servicios recurrentes o programados de la empresa (origen, destino, horarios, código de servicio). |
| RF-09-Recepción de solicitudes de transporte | El sistema deberá recibir solicitudes de transporte de los pasajeros, validarlas y registrarlas en la cola de asignación. |
| RF-10-Asignación automática de conductores | El sistema deberá asignar automáticamente un conductor y un vehículo a cada solicitud pendiente, aplicando las reglas de negocio programadas y configurables del tenant. |
| RF-11-Aplicación de reglas de negocio para la asignación | El sistema deberá aplicar reglas de negocio configurables por tenant, tales como disponibilidad programada, minimización de cambios de turno, balance de carga, distancia del servicio origen-destino y restricciones regulatorias. La telemetría GPS se usa para monitoreo y desviación de ETA, no para reasignación dinámica por cercanía. |
| RF-12-Reasignación manual de conductores | El sistema deberá permitir al Operador logístico reasignar manualmente una asignación cuando exista una contingencia operativa, por ejemplo, cuando un conductor abandone su turno o quede indisponible. |
| RF-13-Priorización de solicitudes urgentes | El sistema deberá priorizar solicitudes marcadas como urgentes o críticas de acuerdo con reglas configuradas por el tenant, sin convertir el motor en un esquema de competencia dinámica por proximidad. |
| RF-14-Recepción de mensajes desde WhatsApp | El sistema deberá recibir mensajes entrantes de pasajero y conductor vía webhook HTTP desde la plataforma WhatsApp Business. La integración se implementa mediante un adaptador desacoplado del proveedor, preservando el contrato funcional del webhook y del envío de mensajes. |
| RF-15-Procesamiento de solicitudes enviadas por WhatsApp | El sistema deberá interpretar los mensajes conversacionales del pasajero, mantener el estado de la conversación y convertirlos en solicitudes de transporte estructuradas. |
| RF-16-Envío de confirmaciones al usuario por WhatsApp | El sistema deberá enviar al pasajero una confirmación por WhatsApp cuando su solicitud haya sido registrada y cuando haya sido asignada. |
| RF-17-Envío de notificaciones al conductor asignado | El sistema deberá notificar al conductor por WhatsApp cuando se le asigne un nuevo servicio, incluyendo los datos del pasajero, origen, destino y hora. |
| RF-18-Actualización de estado del viaje desde WhatsApp | El sistema deberá permitir al conductor actualizar el estado del viaje (inicio, finalización, incidente) enviando mensajes por WhatsApp que se sincronicen con el estado interno del sistema. |
| RF-19-Aislamiento físico entre tenants (modelo Silo) | El sistema deberá garantizar aislamiento físico entre operadores de transporte (tenants) mediante el modelo Silo, evitando que una sesión o proceso de un operador acceda a la persistencia de otro. |
| RF-20-Configuración separada de usuarios y recursos por tenant | El sistema deberá permitir que cada tenant tenga su propia configuración de usuarios, conductores, vehículos, reglas de asignación y parámetros operativos dentro de su instancia Silo. |
| RF-21-Configuración avanzada de reglas de asignación | El sistema deberá permitir definir, activar, desactivar y ordenar reglas de asignación aplicables al tenant (por ejemplo: disponibilidad programada, minimización de cambios de turno, balance de carga, distancia del servicio y restricciones regulatorias). No se usa cercanía GPS para reasignación dinámica. |
| RF-22-Cierre de sesión | permite al usuario cerrar su sesión activa e invalidar el contexto local. |
| RF-23-Recuperación o restablecimiento de credenciales | permite al usuario recuperar el acceso mediante correo electrónico. |
| RF-24-Actualización de información de usuarios | permite modificar datos personales de los usuarios existentes. |
| RF-25-Activación e inactivación de usuarios | permite al Administrador del operador habilitar o deshabilitar el acceso de un usuario. |
| RF-26-Registro de conductores | permite dar de alta un nuevo conductor con sus datos operativos y licencia. |
| RF-27-Actualización de datos de conductores | permite modificar información del conductor. |
| RF-28-Activación e inactivación de conductores | permite habilitar o deshabilitar operativamente a un conductor. |
| RF-29-Validación de datos mínimos de solicitud | verifica que la solicitud contenga los campos obligatorios. |
| RF-30-Consulta del estado de solicitudes | permite al pasajero u operador ver el estado actual de una solicitud. |
| RF-31-Historial de solicitudes y viajes | permite consultar el histórico de solicitudes y viajes por usuario o cliente empresarial. |
| RF-32-Modificación o cancelación de solicitudes | permite cancelar o ajustar una solicitud conforme a las reglas del flujo operativo. |
| RF-33-Visualización de asignaciones generadas | permite al operador ver las asignaciones creadas por el motor. |
| RF-34-Actualización del estado de asignación | permite marcar una asignación como aceptada, rechazada, en curso o finalizada. |
| RF-35-Envío de recordatorios automáticos | envía recordatorios programados de viajes próximos al pasajero y al conductor. |
| RF-36-Visualización centralizada de solicitudes y viajes | muestra una vista unificada de la operación. |
| RF-37-Monitoreo operativo de servicios en curso | permite ver en tiempo real los servicios activos. |
| RF-38-Consulta de usuarios, conductores y asignaciones | permite consultar el catálogo operativo del tenant. |
| RF-39-Intervención manual en la operación | permite al Operador logístico tomar control manual de un servicio cuando exista una contingencia. |
| RF-40-Consulta de trazabilidad de cada viaje | muestra el histórico completo de eventos de un viaje. |
| RF-41-Búsqueda y filtrado de información | permite filtrar y buscar en los listados operativos. |
| RF-42-Visualización de indicadores básicos | muestra métricas operacionales simples de la operación diaria. |
| RF-43-Notificación automática de cambios de estado | notifica al usuario cuando cambia el estado de su servicio. |
| RF-44-Notificación de reasignación o novedades | informa al pasajero y conductor sobre cambios operativos relevantes. |
| RF-45-Alertas operativas para administradores u operadores | notifica eventos que requieren atención. |
| RF-46-Reporte de viajes realizados | genera reporte de viajes completados en un período. |
| RF-47-Reporte de solicitudes atendidas y pendientes | muestra el estado agregado de solicitudes. |
| RF-48-Reporte de conductores asignados | muestra actividad y carga de trabajo por conductor. |
| RF-49-Reporte histórico de operación por cliente empresarial | genera un reporte agregado histórico dentro del tenant. |
| RF-50-Registro de eventos del sistema | registra eventos operativos para trazabilidad técnica. |
| RF-51-Registro de errores y excepciones | registra errores técnicos con contexto para diagnóstico. |
| RF-52-Seguimiento de acciones de usuarios administrativos | registra en auditoría las acciones sensibles. |
| RF-53-Monitoreo técnico de disponibilidad del sistema | expone métricas de disponibilidad y salud del sistema. |
| RF-54-Calificación del servicio | El sistema deberá permitir que el pasajero califique al conductor al finalizar un Viaje, mediante un puntaje y comentario opcional. |
| RF-55-Ingesta de telemetría GPS | **Fuera del alcance de V1** (ADR-0005 en estado *Proposed*). El sistema deberá recibir y almacenar eventos de ubicación de los vehículos/conductores para viajes en curso. |
| RF-56-Detección de desviación de ETA | **Fuera del alcance de V1** (depende de RF-55 y ADR-0005). El sistema deberá detectar desviaciones relevantes de ETA durante viajes en curso a partir de la telemetría GPS y generar una alerta operativa. |

| RF-05-Creación de usuarios por tenant | El sistema deberá permitir al administrador crear usuarios del tenant (pasajeros, conductores, operadores logísticos y administradores) con el rol y asociación operacional correspondiente. | Valor de negocio | Alta de usuarios dentro del tenant. Sin itinerario no hay servicio que asignar. | empresaId, cuando aplique, identifica al cliente empresarial atendido dentro del tenant. |
| RF-09-Recepción de solicitudes de transporte | El sistema deberá recibir solicitudes de transporte de los pasajeros, validarlas y registrarlas en la cola de asignación. | Valor de negocio | Core del negocio. | RF-11-Aplicación de reglas de negocio para la asignación | El sistema deberá aplicar reglas de negocio configurables por tenant, tales como disponibilidad programada, minimización de cambios de turno, balance de carga, distancia del servicio origen-destino y restricciones regulatorias. La telemetría GPS se usa para monitoreo y desviación de ETA, no para reasignación dinámica por cercanía. | Ambos | Motor de reglas configurable por operador, orientado a turnos y programación. La telemetría no se usa para competencia dinámica por cercanía. | Las reglas priorizan disponibilidad programada, balance de carga, turnos y restricciones operativas/regulatorias. |

| RF-13-Priorización de solicitudes urgentes | El sistema deberá priorizar solicitudes marcadas como urgentes o críticas de acuerdo con reglas configuradas por el tenant, sin convertir el motor en un esquema de competencia dinámica por proximidad. | Ambos | Permite priorización operativa según reglas del tenant y gestión de excepciones sin convertir el motor en ride-hailing por proximidad. | La urgencia se resuelve con reglas y alertas operativas, no con un esquema ride-hailing. |
| RF-14-Recepción de mensajes desde WhatsApp | El sistema deberá recibir mensajes entrantes de pasajero y conductor vía webhook HTTPS desde la plataforma WhatsApp Business. La integración se implementa mediante un adaptador desacoplado del proveedor, preservando el contrato funcional del webhook y del envío de mensajes. | Ambos | Canal principal para pasajero y conductor. Reto técnico: webhooks, contrato de integración, idempotencia, seguridad y desacople del proveedor mediante un adaptador específico. | La integración usa un adaptador desacoplado del proveedor concreto de WhatsApp Business. |
| RF-15-Procesamiento de solicitudes enviadas por WhatsApp | El sistema deberá interpretar los mensajes conversacionales del pasajero, mantener el estado de la conversación y convertirlos en solicitudes de transporte estructuradas. | Reto técnico | Parseo conversacional + máquina de estados de conversación. No es CRUD; requiere investigar patrones de bots conversacionales. | Requiere persistencia de contexto y una máquina de estados conversacional. |
| RF-16-Envío de confirmaciones al usuario por WhatsApp | El sistema deberá enviar al pasajero una confirmación por WhatsApp cuando su solicitud haya sido registrada y cuando haya sido asignada. | Valor de negocio | Cierra el flujo. Sin confirmación bidireccional, el pasajero no sabe si su solicitud fue procesada. | WhatsApp es el canal único del pasajero para confirmaciones operativas. |
| RF-17-Envío de notificaciones al conductor asignado | El sistema deberá notificar al conductor por WhatsApp cuando se le asigne un nuevo servicio, incluyendo los datos del pasajero, origen, destino y hora. | Valor de negocio | Cierra el otro extremo del flujo. Sin esto, la asignación no llega al conductor. | WhatsApp es el canal único del conductor para recibir asignaciones. |
| RF-18-Actualización de estado del viaje desde WhatsApp | El sistema deberá permitir al conductor actualizar el estado del viaje (inicio, finalización, incidente) enviando mensajes por WhatsApp que se sincronicen con el estado interno del sistema. | Reto técnico | Reto técnico: mantener sincronización bidireccional entre el estado del sistema y el estado reportado por conductor vía chat. | Debe conservar consistencia entre el estado conversacional y el estado interno del viaje. |
| RF-19-Aislamiento físico entre tenants (modelo Silo) | El sistema deberá garantizar aislamiento físico entre operadores de transporte (tenants) mediante el modelo Silo, evitando que una sesión o proceso de un operador acceda a la persistencia de otro. | Ambos | Diferenciador confirmado: un tenant = un operador de transporte con persistencia físicamente aislada. empresaId identifica al cliente empresarial dentro de la BD del operador y no funciona como filtro entre tenants. | Un tenant = un operador de transporte. El aislamiento es físico (Silo), no un filtro global por empresaId. |
| RF-20-Configuración separada de usuarios y recursos por tenant | El sistema deberá permitir que cada tenant tenga su propia configuración de usuarios, conductores, vehículos, reglas de asignación y parámetros operativos dentro de su instancia Silo. | Reto técnico | Configuración independiente por tenant dentro de su instancia Silo, sin compartir persistencia con otros operadores. | Cada operador mantiene configuración y persistencia independientes dentro de su instancia Silo. |
| RF-21-Configuración avanzada de reglas de asignación | El sistema deberá permitir definir, activar, desactivar y ordenar reglas de asignación aplicables al tenant (por ejemplo: disponibilidad programada, minimización de cambios de turno, balance de carga, distancia del servicio y restricciones regulatorias). | RF-54-Calificación del servicio | El sistema deberá permitir que el pasajero califique al conductor al finalizar un Viaje, mediante un puntaje y comentario opcional. | Valor de negocio | Capacidad incluida explícitamente en V1. Agrega trazabilidad de calidad operacional sobre Viaje y alimenta reportes básicos. | Nueva capacidad V1: entidad Calificacion vinculada a Viaje y disponible para reportes operacionales básicos. |
| RF-55-Ingesta de telemetría GPS | **Fuera del alcance de V1** (ADR-0005 en estado *Proposed*). El sistema deberá recibir y almacenar eventos de ubicación de los vehículos/conductores para viajes en curso. | Ambos | Prevista originalmente para V1 y aplazada (ADR-0005). | RF-56-Detección de desviación de ETA | **Fuera del alcance de V1** (depende de RF-55 y ADR-0005). El sistema deberá detectar desviaciones relevantes de ETA durante viajes en curso a partir de la telemetría GPS y generar una alerta operativa. | Ambos | Usa telemetría para monitoreo de viajes en curso y alertas de desviación. No cambia el motor a asignación dinámica por proximidad. | Nueva capacidad V1: usa telemetría para monitoreo y alertas de desviación de ETA; no modifica el motor de asignación. |
